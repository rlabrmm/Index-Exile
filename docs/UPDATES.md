# Repeat for every TA and ESCU update

1. Start an update record from `docs/UPDATE_LOG_TEMPLATE.md`. Record source versions and hashes without raw logs or credentials. Keep the last accepted build and Git commit available.
2. Place whichever complete updated application packages are available in an untracked directory, safely unpacked under their app IDs. Neither development CSV is required. Do not overwrite the previous input snapshot. Missing application updates mean unchanged applications, not deleted ones.
3. Run `python scripts/review_updates.py --baseline build --updates ../new-updates --output private/update-review.json`. This works with a TA-only or ESCU-only update and identifies changed files, added/removed/changed rules, configuration-setting hashes and new type predicates. It does not need raw samples, the mapping CSV or unchanged app sources. Archives must be safely unpacked first; isolated config fragments require a scoped manual comparison rather than treating them as a complete application.
4. For full packaging, combine the updated applications with unchanged source applications and run `python scripts/build.py --inputs INPUTS --previous-build build --output build-next`. An automatic comparison is written to `build-next/reports/update_diff.json`. Preserve `config/auditd_catalog.json` and prior model knowledge; absent samples never remove fields/datasets. Optional `--samples PATH` and `--type-map PATH` add development evidence. Existing `[auditd]` or `ix_auditd*` stanza collisions stop for a reviewed merge. Report real search removals and schema changes explicitly; do not silently retire a consumed child.
5. Review all changed TA components: props/transforms/eventtypes/tags, default/local precedence, macros/lookups, metadata, inputs, scripts and manifests. Review changed extraction semantics separately from package-version changes. Preserve vendor licenses and unrelated functionality.
6. Update the generator/policy and tests, then regenerate from pristine inputs. Do not hand-edit generated output without backporting it to source. Run local tests, archive verification and secret checks. Compare package content to staged app trees.
7. Validate supported server/version behavior, effective configuration and result equality on the test environment through the installed Splunk skills. Never treat static Python regex tests as Splunk validation. If the required runtime tool is missing, preserve the local deliverable and record live validation as not executed.
8. Run the conversion skill with the new inventory. Every source or candidate change invalidates prior approval. Validate time windows, macro/filter context, nulls, multiplicity, schedule/risk fields and summary completeness.
9. Present the exact per-rule diff and evidence to the human approver. Generate search-only patches only from explicit approvals. Deployment, reload/restart and detection activation are separate controlled steps.
10. Close the stage log with changed paths, test outcomes, remaining limits and rollback target. Scan the exact staged Git files. Commit only the portable reviewed output, with an English message; never push unless requested.

Both skills are reusable directories with SKILL.md frontmatter. Copy the directory into the target agent's supported skill location, or explicitly invoke/read its SKILL.md while keeping this repository available. Repository-relative paths are intentional; no machine-specific credentials or addresses are embedded.

The setting-level baseline covers TA configuration and detection-relevant ES/ESCU configuration. Other application files still have whole-file hash comparisons. Setting values and secret-bearing setting hashes are not exported. The first comparison against an older build without setting-level hashes explicitly reports that limitation; file/rule comparison still works.
